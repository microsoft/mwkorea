# 에이전트를 메이커끼리 나눠 씁니다: Copilot Studio의 Agent Sharing

에이전트를 혼자 만드는 경우는 생각보다 적습니다. 업무를 잘 아는 사람이 시나리오를 잡고, 기술에 익숙한 사람이 도구 연결을 맡고, 관리자가 게시 전 검토를 합니다. 그런데 지금까지 새 GitHub Copilot harness 환경에서는 **이 협업을 위한 공유 수단**이 마땅치 않았습니다.

메시지 센터 공지 **RM569475**로 안내된 **Agent Sharing amongst makers**는 이 부분을 채웁니다. **에이전트를 다른 메이커와 공유**할 수 있게 되고, 역할에 따라 권한을 나눠 부여합니다.

---

## 무엇이 달라지나요

Microsoft가 공지에서 밝힌 내용입니다.

> **새 GHCP harness**에서 다른 메이커와 에이전트를 공유할 수 있습니다. 메이커는 다른 메이커에게 **Agent Viewer**(분석·평가만 조회) 또는 **Editor**(조회, 편집, 구성, 공유, 게시) 접근 권한을 부여할 수 있으며, **보안 역할이 자동 할당(auto-assigned security roles)** 됩니다.

여기서 **GHCP harness**는 GitHub Copilot harness를 가리킵니다.

### 두 가지 권한 수준

| 권한 | 할 수 있는 것 |
|---|---|
| **Agent Viewer** | **분석(analytics)·평가(evaluations) 조회만** |
| **Editor** | **조회, 편집, 구성, 공유, 게시** |

권한 설계가 명확히 나뉘어 있습니다. Viewer는 **결과를 보는 사람**, Editor는 **에이전트를 바꾸는 사람**입니다.

주목할 점은 Editor에 **공유(share) 권한이 포함**된다는 것입니다. Editor를 받은 메이커는 다시 다른 사람에게 공유할 수 있습니다.

### 보안 역할 자동 할당

공유 시 **보안 역할이 자동으로 할당**됩니다. 메이커가 Dataverse 보안 역할을 직접 찾아 설정하지 않아도 된다는 뜻으로, 공유 과정의 마찰을 줄이는 부분입니다.

---

## 왜 의미가 있나요

에이전트 개발이 개인 작업에서 팀 작업으로 넘어가는 단계에서 필요한 기능입니다. 구체적으로 이런 상황이 풀립니다.

- **업무 담당자 + 기술 담당자 협업** — 시나리오를 아는 사람과 구현하는 사람이 같은 에이전트를 함께 다룸
- **검토·승인 흐름** — 배포 전 다른 메이커가 구성을 확인
- **품질 모니터링** — 만들지 않은 사람도 **분석과 평가 결과를 볼 수 있음**(Viewer)
- **담당자 인수인계** — 만든 사람이 바뀌어도 에이전트가 고립되지 않음
- **Copilot 챔피언 운영** — 부서별 챔피언이 서로의 에이전트를 참고

특히 **Viewer 권한이 분석·평가에 한정**되어 있다는 설계가 흥미롭습니다. 에이전트를 건드리지 않으면서 **품질 지표만 공유**하고 싶을 때 쓰기 좋습니다. 최근 Copilot Studio가 평가(Evaluations) 경험을 강화하고 있는 흐름과도 맞물립니다.

---

## 활용 시나리오 예시

**시나리오 1 — 개발과 검토 분리**
에이전트를 만든 메이커가 검토자에게 **Viewer** 권한을 줘서 평가 결과와 분석 지표만 확인하게 합니다. 구성은 변경되지 않습니다.

**시나리오 2 — 공동 개발**
같은 팀의 다른 메이커에게 **Editor** 권한을 부여해 지시문과 도구 구성을 함께 다듬습니다.

**시나리오 3 — 운영 인수인계**
담당자 변경 시 새 담당자에게 Editor를 부여하고, 기존 담당자는 Viewer로 낮춰 모니터링만 이어 갑니다.

## 메이커·도입 담당자를 위한 체크포인트

- **Editor의 재공유 권한에 주의**: Editor 권한에는 **공유(share)** 가 포함됩니다. 한 사람에게 Editor를 주면 그 사람이 또 다른 사람에게 권한을 줄 수 있습니다. **누가 Editor를 받을지에 대한 조직 기준**을 정해 두는 것이 좋습니다.
- **Viewer를 기본값으로 고려**: 검토·모니터링 목적이라면 Viewer로 충분합니다. **필요한 최소 권한 원칙**을 적용하세요.
- **자동 할당되는 보안 역할 파악**: 공유 시 보안 역할이 자동 할당되므로, **그 역할이 어떤 Dataverse 권한을 포함하는지** 관리자가 미리 확인해 두면 좋습니다. 편의성과 통제 사이의 균형점이 여기에 있습니다.
- **적용 범위는 GHCP harness**: 공지는 **새 GHCP(GitHub Copilot) harness**를 명시합니다. 표준 harness 에이전트에서의 동작은 별도 확인이 필요합니다.
- **게시 권한의 무게**: Editor에는 **게시(publish)** 가 포함됩니다. 프로덕션 배포 통제가 필요한 조직이라면, Editor 부여를 게시 승인 절차와 연결해 생각해야 합니다.
- **크레딧 소비와의 연결**: GitHub Copilot harness는 **빌드·미리 보기·평가 단계에서도 크레딧을 소비**합니다. 공유로 에이전트를 다루는 메이커가 늘면 그만큼 개발 단계 소비도 늘어납니다. **소비 모니터링 체계와 함께** 검토하세요.
- **공유 현황 가시성 확보**: 공유가 쉬워질수록 "누가 어떤 에이전트에 접근 권한이 있는지" 파악이 중요해집니다. 관리 측면의 조회 방법을 출시 후 확인해 두세요.

---

## 마무리

에이전트가 개인의 실험에서 **팀의 자산**으로 넘어가려면 공유는 필수 조건입니다. 이번 기능은 그 문턱을 낮추면서도 **Viewer / Editor 두 단계로 권한을 나눠** 무분별한 개방을 피하는 설계를 택했습니다.

다만 Editor에 공유와 게시가 함께 들어 있다는 점은 조직 차원에서 규칙이 필요한 부분입니다. 편해진 만큼 **누구에게 어디까지 열어 줄지**를 정해 두는 것이 이번 기능을 잘 쓰는 방법이 되겠습니다.
