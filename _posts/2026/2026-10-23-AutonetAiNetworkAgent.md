# 네트워크 변경을 대화로 준비한다: Microsoft Autonet AI Agent의 설계와 승인 원칙

네트워크 엔지니어의 시간을 잡아먹는 것은 도구의 부족만이 아닙니다. 구성 저장소, 상태 조회, 검증 도구, 변경 절차를 오가며 **작업에 필요한 맥락을 모으는 일**도 큰 부담입니다.

Microsoft의 사내 IT 조직인 Microsoft Digital은 이 문제를 **Autonet AI Agent**라는 대화형 진입점으로 풀고 있습니다. 엔지니어가 원하는 결과를 자연어로 설명하면, 플랫폼이 필요한 정보와 전문 기능을 연결해 변경안을 준비합니다. 중요한 점은 실제 변경 전에 사람에게 알리고 **승인을 기다린다**는 것입니다.

Inside Track 원문은 2026년 10월 22일 15:45 UTC, 한국 시간으로 **10월 23일 00:45**에 게시되었습니다. 발표 시점의 Autonet AI Agent는 비교적 적은 프로세스를 대상으로 한 **Microsoft 내부 파일럿**입니다. 고객용 정식 출시 제품이나 즉시 설치 가능한 네트워크 자동화 패키지로 소개된 것은 아닙니다.

---

## 도구를 찾는 대신, 원하는 결과를 설명하기

기존에는 네트워크 요청 하나를 처리할 때도 현재 구성 확인, 상태 검증, 영향받는 장비 파악, 변경안 작성, 롤백 준비, 승인 절차를 서로 다른 시스템에서 수행해야 했습니다.

Autonet AI Agent는 이를 **conversational front door**, 즉 하나의 대화형 입구로 묶습니다. 사용자는 결과 중심으로 요청하고, 뒤에서는 필요한 맥락을 수집하고 적절한 작업 흐름을 조율합니다.

![Autonet AI Agent의 대화형 진입점 구상을 설명한 Sai Madhav Tiruvuri](/mwkorea/assets/images/2026-10-23-AutonetAiNetworkAgent/image1.png)

모든 기능을 하나의 거대한 에이전트에 넣는 방식은 아닙니다. 전문 에이전트가 각자의 역할을 맡습니다.

| 구성 요소 | 원문에 소개된 역할 |
|---|---|
| IP Helper Agent | IP helper 데이터 조회 |
| Core WAN agent | 구성 템플릿 관리 |
| Intake Agent | 들어오는 작업 흐름 처리 |
| Autonet AI Agent 플랫폼 | 전문 기능과 작업 흐름을 공통 경험으로 연결·조율 |

예를 들어 IP Helper Agent는 Intake Agent와 연결될 수 있습니다. 네트워크 팀들이 이미 만든 에이전트를 통합하기 위해 포털, 셸, 구성 요소, **Model Context Protocol(MCP) 규칙과 서버**도 설계했습니다.

팀별 전문성을 살리되, 보안·개인정보 보호·책임 있는 AI 기준을 충족하도록 검토와 거버넌스 절차를 적용합니다. 새로운 전문 에이전트가 추가되어도 사용자는 같은 진입점에서 작업할 수 있다는 것이 플랫폼 접근의 장점입니다.

## AI보다 먼저 준비한 것은 신뢰할 수 있는 데이터

Microsoft Digital은 분산된 시스템에 AI를 곧바로 연결하기보다, **관리되는 단일 기준 저장소(source of truth)**를 먼저 마련했습니다. 이 저장소는 네트워크 구성 데이터를 담고 엔지니어, API, 파트너 도구, 자동화, AI 경험이 공통으로 참고하는 기반이 됩니다.

여기서 중요한 것은 데이터가 한곳에 있다는 사실뿐 아니라, **어떤 정보가 권위 있는 현재 상태인가**를 정하는 것입니다. 원문은 이를 네트워크 이외의 에이전트 도입에도 적용되는 선행 과제로 제시합니다.

![기존 자동화 위에서 AI가 작업 준비를 돕는 구조를 설명한 Faris Mango](/mwkorea/assets/images/2026-10-23-AutonetAiNetworkAgent/image2.png)

국내 조직에서도 에이전트 개발 전에 장비·사이트·구성의 기준 저장소와 갱신 책임을 확인할 필요가 있습니다. 이 점검은 원문에서 도출한 적용 제안이며, 특정 저장소 제품이 필수라는 의미는 아닙니다.

## AI의 해석과 결정적 자동화의 실행을 나누기

네트워크 운영에는 결과가 예측 가능하고 반복 가능해야 하는 단계가 많습니다. 검증 루틴, 배포 파이프라인, 승인 절차, 구성 배포를 모두 자유로운 AI 판단으로 바꾸는 것은 이 사례의 방향이 아닙니다.

원문이 제시하는 역할 분담은 다음과 같습니다.

| AI가 맡는 영역 | 기존 결정적 자동화가 맡는 영역 |
|---|---|
| 요청 의도 해석 | 정해진 검증 루틴 실행 |
| 맥락과 관련 정보 수집 | 배포 파이프라인의 반복 가능한 실행 |
| 전문 기능·시스템 간 조율 | 승인 및 구성 배포 절차의 일관된 처리 |

즉, 이미 투자한 자동화를 버리는 대신 **자동화에 필요한 입력과 판단 자료를 준비하는 수고**를 줄입니다. 결정적 자동화는 같은 규칙과 입력에 대해 예측 가능한 결과를 내는 역할을 유지합니다.

## 변경 요청이 들어오면 어떤 일을 준비하나요?

초기 활용 사례 중 하나는 네트워크 구성의 **렌더링과 검증**입니다. 구성은 템플릿, 업무 로직, 기준 저장소의 데이터에 의존하므로, 작은 수정도 장비 유형과 배포 시나리오에 따라 영향을 달리할 수 있습니다.

![구성 렌더링과 버전 비교 경험을 설명한 Pruthvish Panakanti](/mwkorea/assets/images/2026-10-23-AutonetAiNetworkAgent/image3.png)

원문이 제시한 변경 요청 처리 흐름은 다음과 같습니다.

1. 요청의 의도를 해석합니다.
2. 영향받는 장비와 위치를 식별합니다.
3. 관련 구성 정보를 조회합니다.
4. 현재 상태와 의도한 상태를 비교합니다.
5. 잠재적인 충돌을 찾습니다.
6. 제안할 구성 변경안을 만듭니다.
7. 롤백 지침을 준비합니다.
8. 검토 가능한 산출물을 생성합니다.

엔지니어는 대화를 이어 가며 네트워크 사실 정보를 확인하고, 최신 데이터를 적용해 구성을 렌더링하고, 버전 간 결과를 비교하며 차이를 조사할 수 있습니다.

![실제 변경 전에 맥락과 검증 자료를 모으는 부담을 설명한 Christopher Kuilan](/mwkorea/assets/images/2026-10-23-AutonetAiNetworkAgent/image4.png)

이 흐름의 가치는 “변경 명령을 자동 생성한다”에만 있지 않습니다. **변경해도 되는지를 사람이 판단할 수 있도록 정보·차이·충돌·복구 지침을 연결한다**는 데 있습니다. 자료 수집은 줄이되, 엔지니어의 판단 책임은 유지합니다.

## 사람의 승인은 선택 사항이 아니라 설계 요건

Autonet AI Agent는 정보를 조회하고, 추천과 산출물을 준비하고, 가능한 행동을 설명합니다. 그러나 **행동이나 변경을 제안하면 엔지니어에게 알리고 승인을 기다립니다.**

![기존 운영 통제 안에서 에이전트를 활용하는 원칙을 설명한 Darron Sullivan](/mwkorea/assets/images/2026-10-23-AutonetAiNetworkAgent/image5.png)

추천의 근거를 살펴볼 수 있는 투명성과 human-in-the-loop 검토는 개발 과정부터 요구사항으로 다뤄졌습니다. 대화형 인터페이스를 제공한다고 해서 기존 변경관리나 승인 절차를 우회하는 것은 아닙니다.

국내 도입 시에도 조회, 변경안 생성, 실제 적용을 별도 권한과 단계로 나누고, 어떤 변경에 누구의 승인이 필요한지 명확히 하는 것이 중요합니다. 이는 사례를 참고한 설계 제안이며, 원문에 공개된 구체적인 권한 설정 명령이나 배포 레시피는 아닙니다.

## 성과 수치는 일부 사례의 범위에서 해석하기

원문은 **일부 IP helper 데이터 조회가 최대 3주에서 하루 이내로 단축**된 사례를 소개합니다.

이는 모든 네트워크 변경의 처리 시간이 하루 이내라는 뜻이 아닙니다. 전체 프로세스 평균이나 보편적인 생산성 향상률도 제시되어 있지 않습니다. 현재는 제한된 프로세스의 파일럿 결과로 이해해야 합니다.

![공통 인터페이스 뒤로 전문 기능을 확장하는 방향을 설명한 Jason Thompson](/mwkorea/assets/images/2026-10-23-AutonetAiNetworkAgent/image6.png)

앞으로는 같은 사용자 경험을 유지하면서 더 많은 전문 기능과 업무 영역을 연결하는 플랫폼 방향을 보고 있습니다. **특정 업무에서 가치를 확인한 뒤 뒤쪽 기능을 확장한다**는 점이 실무적으로 참고할 만합니다.

## 우리 조직에서 시작할 때의 체크포인트

유사한 Copilot·에이전트 경험을 설계하려면 먼저 다음을 정리할 수 있습니다.

- **기준 데이터**: 현재 상태를 대표하는 저장소와 갱신 책임을 정합니다.
- **업무 범위**: 조회·렌더링·비교처럼 효과와 위험을 측정하기 쉬운 프로세스부터 고릅니다.
- **역할 분담**: AI의 해석·조율과 결정적 검증·실행의 경계를 명시합니다.
- **검토 자료**: 변경 전후 차이, 영향 범위, 검증 결과, 롤백 지침을 사람이 확인할 수 있게 합니다.
- **승인 통제**: 실제 변경은 기존 운영 통제와 승인 책임 안에서 수행합니다.
- **확장 구조**: 전문 에이전트를 추가해도 사용자의 진입점과 관리 원칙이 흔들리지 않도록 합니다.

원문은 관련 출발점으로 [Microsoft Agent 365 문서](https://learn.microsoft.com/en-us/microsoft-agent-365/)와 [Microsoft 내부 Agent 365 도입 경험](https://www.microsoft.com/insidetrack/blog/implementing-agent-365-how-were-governing-and-managing-ai-agents-at-microsoft/)을 안내합니다. Agent 365를 시작하면 Autonet이 자동으로 제공된다는 뜻은 아니며, 개발·관리 도구는 조직의 요구에 맞게 별도로 선택해야 합니다.

Autonet 사례의 핵심은 **대화가 운영 통제를 대체하는 것이 아니라, 신뢰할 수 있는 데이터와 기존 자동화로 들어가는 입구를 단순하게 만든다**는 것입니다. 사람이 더 적은 시간을 자료 수집에 쓰고, 더 많은 시간을 전문적인 판단에 쓰도록 하는 접근입니다.
