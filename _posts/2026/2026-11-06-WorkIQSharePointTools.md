# Work IQ에 SharePoint 도구가 들어왔다: 검색부터 승인까지, 에이전트가 직접 일하는 방법

사내 에이전트가 SharePoint 문서를 찾아 답변하는 것과, 그 문서를 바탕으로 실제 업무를 처리하는 것은 다른 문제입니다. 목록을 만들거나 승인 관련 작업을 수행하려면 어떤 작업을 호출할 수 있는지, 어떤 인자를 넣어야 하는지, 누구의 권한으로 실행하는지까지 알아야 합니다.

Microsoft는 2026년 11월 6일 Microsoft 365 Developer Blog에서 **Work IQ: SharePoint Tools**를 소개했습니다. Microsoft Copilot을 뒷받침하는 업무 인텔리전스 계층을 사용자 정의 앱과 에이전트에 연결하고, SharePoint의 콘텐츠와 작업을 함께 활용하게 하는 방향입니다.

핵심은 **작업별 도구를 모두 미리 등록하는 대신, 실행 시점에 필요한 작업과 스키마를 발견한다**는 점입니다. 원문은 SharePoint MCP를 프리뷰로 명시합니다. 이 글 역시 해당 발표 시점을 기준으로 설명하며, 모든 기능의 GA나 모든 테넌트에서의 즉시 이용을 의미하지 않습니다.

---

## 새로운 도구는 어디까지 다루나요?

SharePoint가 호스팅하는 인증된 MCP 엔드포인트를 통해 SharePoint의 기능을 Work IQ에 제공합니다. 원문에 소개된 카탈로그는 **60개가 넘는 SharePoint 작업**을 포함합니다.

| 영역 | 원문에서 소개한 범위 |
|------|--------------------|
| 콘텐츠 구조 | 목록, 라이브러리, 목록 항목 |
| 문서 작업 | 파일, 폴더, 검색 |
| 업무 처리 | 승인, 규칙, Quick Steps |
| 콘텐츠 관리 | 휴지통, 버전 관리 |

이 범위는 제공자 카탈로그의 설명이지, 특정 사용자에게 모든 작업 권한이 부여된다는 뜻은 아닙니다. 실제로 사용할 수 있는 작업은 권한과 반환된 스키마를 확인해야 합니다.

Work IQ는 조직의 지식·사람·업무 흐름에 맥락, 메모리, 스킬을 결합하는 계층입니다. 이번 SharePoint 도구는 그 맥락을 이용해 **질문에 답하는 단계에서 실제 SharePoint 작업을 수행하는 단계**로 넘어가기 위한 연결점입니다.

## 구현의 핵심: 먼저 발견하고, 스키마를 읽고, 실행하기

에이전트가 60여 개 작업을 각각 별도의 도구로 노출할 필요는 없습니다. Work IQ는 고정된 범용 도구 체계를 제공하고, 에이전트가 필요한 SharePoint 경로를 런타임에 발견하도록 합니다.

1. 대상 사이트에 대해 `get_site_key`를 호출해 사이트 컨텍스트를 확보합니다.
2. `search_paths`로 필요한 작업을 찾습니다.
3. 반환된 경로를 `get_schema`에 전달해 필수 인자와 타입을 확인합니다.
4. 확인한 스키마에 맞춰 요청 본문을 구성하고 `do_action`으로 실행합니다.

SharePoint 제공자는 등록된 `sharepoint/` 접두 아래의 경로를 처리합니다. **경로 이름을 추측해서 호출하지 말고, 탐색 결과를 그대로 사용해야 합니다.**

다음은 원문이 설명한 흐름을 이해하기 위한 의사 코드입니다. 실행 가능한 SDK 예제나 특정 작업의 실제 경로를 의미하지 않습니다.

```text
get_site_key(siteUrl: "https://contoso.sharepoint.com/sites/project")
  → 이 사이트의 siteKey 보관

search_paths(...)
  → 필요한 SharePoint 작업 경로 발견

get_schema(path: "<탐색 결과로 반환된 경로>")
  → 필수 인자와 타입 확인

do_action(
  "<탐색 결과로 반환된 경로>",
  body: {
    siteKey: "<해당 사이트에서 반환된 불투명 키>",
    ...스키마에 맞춘 인자...
  }
)
```

검색 결과에는 선택한 작업에 따라 페이지·파일·목록 항목 등과 후속 호출에 사용할 식별자 및 URL이 포함될 수 있습니다. 반환 형태도 작업마다 다르므로 고정된 응답 구조를 가정하지 않는 것이 중요합니다.

## 개발자가 놓치기 쉬운 세 가지 세부사항

### siteKey는 사이트 URL이 아닙니다

사이트를 대상으로 하는 작업은 일반적으로 원시 URL 대신 **불투명한 `siteKey`**를 사용합니다. 대상 사이트에서 한 번 얻은 키를 변경하지 않고 후속 작업에 전달하며, 다른 사이트에 재사용하지 않아야 합니다.

### 쓰기 작업은 SharePoint 내부 필드 이름을 사용합니다

화면에 보이는 열 표시 이름이 그대로 쓰기 요청에 들어간다고 가정하면 안 됩니다. 사람·조회·분류 체계 필드의 값은 반환된 스키마에 따라 해석하고 구성해야 합니다. 한국어 열 이름을 사용하는 사내 목록에서도 표시 이름과 내부 이름의 차이를 확인해야 합니다.

### 일부 인자는 JSON 문자열일 수 있습니다

Work IQ 범용 도구 계약에서는 `items`, `folders`, `viewIds` 같은 인자가 중첩 객체가 아니라 **JSON으로 인코딩된 문자열**로 표현될 수 있습니다. 모든 인자를 임의로 문자열화하는 것도, 모두 객체로 보내는 것도 피하고 `get_schema`의 타입을 정확히 따라야 합니다.

## 권한 모델: WorkIQ.Read와 WorkIQ.Act

원문은 접근을 세분화하기 위한 두 권한 범위인 `WorkIQ.Read`와 `WorkIQ.Act`를 소개합니다. SharePoint 도구에 접근하려면 에이전트에 이 중 하나의 범위가 필요합니다.

| 권한 범위 | 원문이 설명한 상위 도구 노출 |
|-----------|-----------------------------|
| `WorkIQ.Read`만 보유 | `fetch`, `call_function`, `get_schema`, `search_paths` 등 변경을 일으키지 않는 작업에 맞춘 축소 도구 집합 |
| `WorkIQ.Act` 보유 | 전체 도구 집합 |

두 범위 모두 **위임 권한**입니다. 각 호출은 로그인한 사용자의 SharePoint 신원으로 수행되므로, 에이전트가 읽거나 변경할 수 있는 대상도 해당 사용자가 이미 접근할 수 있는 범위로 제한됩니다.

따라서 `WorkIQ.Act`를 부여했다고 해서 사용자에게 없는 사이트 권한이나 관리자 권한이 생기지는 않습니다. 도입 시에는 앱의 권한 범위와 실제 사용자의 SharePoint 접근 권한을 별도로 점검해야 합니다.

## 한국 조직의 개발·도입 체크포인트

다음은 원문의 기술 설명을 바탕으로 정리한 **실무 권고**이며, 별도의 제품 기능이나 Microsoft의 의무 정책을 뜻하지 않습니다.

- **조회와 변경 시나리오를 나누기**: 문서 탐색·답변용 에이전트와 목록 생성·승인 업무용 에이전트의 필요한 권한을 구분합니다.
- **탐색 결과를 요청 생성의 근거로 쓰기**: 작업 경로, 필드 타입, 필수 인자를 하드코딩하기보다 실제 반환 스키마와 일치시키도록 설계합니다.
- **사이트별 컨텍스트를 분리하기**: 여러 부서 사이트를 다룰 때 `siteKey`가 섞이지 않도록 합니다.
- **변경 작업의 검토 지점을 설계하기**: 목록·파일·승인 관련 변경은 사용자 확인과 실행 결과 확인을 업무 흐름에 맞게 배치합니다.
- **프리뷰 전제를 확인하기**: 도입 시점의 공식 문서에서 이용 조건과 현재 지원 범위를 확인합니다. 원문에 없는 한국어 지원 범위나 라이선스 조건을 임의로 확정하지 않습니다.

처음부터 모든 SharePoint 작업을 자동화하기보다는, 특정 프로젝트 사이트에서 검색하고 필요한 목록 작업을 수행하는 작은 시나리오로 시작하는 편이 구현과 권한 검증을 함께 진행하기 좋습니다.

이번 변화의 의미는 도구 개수 자체보다 **에이전트가 필요한 작업을 발견하고, 계약을 이해하고, 사용자 권한 안에서 실행하도록 연결한다**는 데 있습니다. SharePoint를 지식 저장소로만 쓰던 에이전트를 실제 업무 처리로 확장하려는 개발자라면 이 패턴을 주목할 만합니다.
