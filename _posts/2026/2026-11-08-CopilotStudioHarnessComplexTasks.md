# Copilot Studio, 복잡한 업무를 끝까지 수행하는 비결: Microsoft Copilot harness 논문 읽기

에이전트에게 질문 하나를 던지는 것과, 한 달치 청구서를 규정에 맞춰 검토하고 결과 보고서까지 만들게 하는 것은 전혀 다른 문제입니다. 후자는 여러 도구를 호출하고, 많은 데이터를 다루고, 중간에 실패해도 다음 방법을 찾아야 합니다. 모델이 똑똑하다는 이유만으로 이런 업무가 저절로 완성되지는 않습니다.

Microsoft Copilot Studio Blog는 **Microsoft Copilot harness가 복잡한 작업 수행을 어떻게 지원하는지** 설명하는 글과 PDF 논문을 공개했습니다. 여기서 harness는 모델 주변에서 작업의 흐름, 도구 사용, 상태와 실행 환경을 연결하는 구조를 뜻합니다. 논문은 기존 **Standard harness**와 **Microsoft Copilot harness**를 비교하며, 같은 모델을 사용해도 실행 구조에 따라 결과가 달라진다고 설명합니다.

이 글은 공개 블로그의 초록뿐 아니라 첨부 논문의 아키텍처, 평가 조건, 운영 데이터까지 함께 읽어 정리했습니다. **제품 출시 공지가 아니라 Microsoft가 보고한 연구·운영 결과에 대한 해설**이며, 특정 모델의 현재 제공 여부나 모든 테넌트의 기능 활성화를 보장하는 글은 아닙니다. 글 날짜는 수집 피드의 `pubDate`를 한국 시간으로 변환한 2026년 11월 8일 기준입니다.

## 핵심 변화: 빠르게 답하는 대화에서, 작업을 이어가는 실행 루프로

논문에 따르면 Standard harness는 2023년 처음 도입됐으며, Microsoft Copilot harness는 2026년 도입됐습니다. 두 방식은 제품 안에 함께 남아 있고, 논문은 하나를 무조건 다른 하나로 교체하자고 주장하지 않습니다.

Standard harness는 한 번의 대화를 의도 파악, 계획과 응답, 누락된 입력 확인 등의 **분리된 모델 호출**로 처리합니다. 좁은 역할별로 조정하기 쉽고 빠르지만, 호출 사이의 상태는 harness가 전달하는 정보에 의존합니다. 도구 결과도 프롬프트에 들어가도록 요약하거나 잘라야 하고, 진행이 막히면 사용자에게 질문하거나 오류를 알려 주는 방식입니다.

Microsoft Copilot harness는 **하나의 모델 중심 루프**를 사용합니다. 작업을 받아 다음 행동을 결정하고, 도구를 실행하고, 결과를 같은 문맥에 추가한 다음 다시 판단합니다. 작업이 완료되거나 실행 예산이 소진될 때까지 이 과정을 이어갑니다.

| 비교 항목 | Standard harness | Microsoft Copilot harness |
|---|---|---|
| 기본 실행 구조 | 한 턴 안의 여러 역할별 모델 호출 | 작업을 진행하는 모델·도구 호출 루프 |
| 문맥 유지 | 호출마다 harness가 필요한 상태 전달 | 루프 전체에서 문맥을 이어감 |
| 실행 환경 | 공유 오케스트레이션 서비스 | 세션별 보안 컨테이너 |
| 도구 | 커넥터, MCP, 지식 소스, code interpreter 등 | 기존 제품 도구에 컨테이너 내부 셸·코드·파일 도구 추가 |
| 큰 데이터 | 프롬프트에 맞춰 요약·절단 | 디스크에 저장하고 코드로 부분 처리 |
| 도구 실패 대응 | 사용자에게 제어를 돌려주는 구조 | 실패를 관찰하고 재시도·대안·질문을 판단 |
| 논문이 설명한 일반적 시간 범위 | 턴당 수초 | 작업당 수분에서 수시간 |

여기서 **턴(turn)**은 한 번의 트리거나 사용자 메시지와 그 응답, **작업(task)**은 완료 판단까지 이어지는 업무 단위, **세션(session)**은 컨테이너의 수명입니다. 작업은 여러 턴에 걸칠 수 있으므로, 턴별 속도와 전체 작업 완료 시간을 같은 지표로 보면 안 됩니다.

## 보안 컨테이너가 추가하는 세 가지 능력

### 1. 실패 이후에도 이어가는 루프

컨테이너 안에서는 계획, 실행, 관찰을 반복합니다. 종료 조건은 무제한 실행이 아니라 **턴 수·시간·토큰 등의 예산**입니다. 실패한 도구 호출 역시 모델이 다음 판단에 활용할 수 있는 관찰 결과가 됩니다.

이 구조는 자동 재시도 횟수를 고정해 두는 것과 다릅니다. 모델은 입력을 수정하거나, 데이터를 먼저 조사하거나, 다른 도구를 선택하거나, 사용자에게 물을 수 있습니다. 다만 계속 실행한다는 사실이 업무를 반드시 성공시킨다는 뜻은 아닙니다.

### 2. 설명하는 대신 코드와 파일로 처리

기본 제공되는 명령줄·코딩·파일 도구로 데이터를 변환하고 검증하며, Word·Excel·PowerPoint·PDF 같은 결과물을 만들고 편집할 수 있다고 논문은 설명합니다.

예를 들어 두 시스템의 내역을 대조하는 업무라면, 모든 행을 자연어로 모델에게 읽히는 대신 코드로 식별자를 비교하고 불일치 목록을 만든 뒤 결과를 검토하는 방식이 가능합니다. 이는 논문의 아키텍처를 업무에 적용한 예시이지, 특정 완제품 템플릿이 제공된다는 의미는 아닙니다.

### 3. 대량 데이터를 프롬프트가 아니라 디스크에 저장

논문은 **50,000행 내보내기**를 예로 듭니다. 이런 결과를 하나의 프롬프트에 넣으려 하기보다, 파일로 저장해 조회·샘플링·집계하는 방식입니다.

중요한 점은 데이터가 사라지는 것이 아니라 처리 위치와 방법이 바뀐다는 것입니다. 필요한 부분을 반복적으로 읽을 수 있지만, 실제 데이터 접근 권한과 보존 정책까지 자동으로 해결되는 것은 아닙니다.

## 거버넌스의 핵심: 판단은 컨테이너, 자격 증명과 제품 도구 실행은 런타임

Microsoft Copilot harness의 구조를 “모델에게 자격 증명과 외부 접근을 모두 넘긴 셸”로 이해하면 잘못입니다. 논문은 다음과 같이 역할을 나눕니다.

| 컨테이너 내부 harness | 컨테이너 외부 Copilot Studio 런타임 |
|---|---|
| 다음 행동과 재시도 여부 판단 | 세션 시작, 메시지 전달, 실행 예산 적용 |
| 내부 코드·파일 도구로 저장된 데이터 처리 | 거버넌스가 적용된 모델 서비스를 통한 모델 호출 중개 |
| 결과를 관찰하며 작업 완료 여부 판단 | 커넥터·MCP·Graph·연결된 에이전트 등의 제품 도구 실행 |
| 세션 동안 작업 파일과 문맥 유지 | 제품 도구 실행에 필요한 자격 증명 보유 |

**자격 증명은 sandbox에 들어가지 않으며, 두 계층 모두 Copilot Studio의 규정 준수 경계 안에 있다**는 것이 논문의 설명입니다. 컨테이너는 서비스 밖으로 나가는 통로가 아니라 서비스 내부 격리 장치입니다. 메모리와 skills는 세션 사이를 이어 주는 요소로 설명되지만, 모든 작업 파일이 세션 종료 뒤 자동 영구 보존된다고 단정할 수는 없습니다.

국내 도입 담당자에게 중요한 구분은 **실행 방식이 더 자율적이어도 권한과 정책의 책임이 사라지지 않는다**는 점입니다. 실제 환경의 연결 계정, 데이터 범위, 보존 조건, 승인 정책은 별도로 확인해야 합니다.

## 같은 모델·같은 과제에서 무엇이 달라졌나

논문의 오프라인 평가는 같은 평가 과제를 두 harness에 같은 모델로 실행하고, 과제별 성공 기준에 따라 통과 여부를 판정했습니다.

| 평가 지표 | GPT-5.5 Chat: Standard → Copilot harness | Opus 4.8: Standard → Copilot harness |
|---|---|---|
| 평가 통과율 | 67.2% → 78.0%, **+10.8%p** | 67.0% → 89.1%, **+22.1%p** |
| 프롬프트 캐시 적중률 | 약 45% → 83% | 약 39% → 88% |
| 작업당 모델 호출 수 | 2.6 → 4.3, 약 1.7배 | 2.3 → 4.8, 약 2배 |
| 작업당 원시 전체 토큰 | 30,839 → 62,610, 약 2배 | 47,675 → 122,864, 약 2.6배 |
| 캐시 정규화 입력 토큰 | 18,211 → 15,551, 약 15% 감소 | 37,215 → 29,499, 약 21% 감소 |
| 모델 호출당 평균 지연 | 3,384ms → 3,054ms, 약 10% 감소 | 5,579ms → 3,578ms, 약 36% 감소 |

캐시 적중률의 시작·끝 값은 표에서 반올림돼 있습니다. 논문이 별도로 보고한 변화량은 각각 **+38.6%p, +48.2%p**입니다. 초록의 “평균 약 +40%p”와 개별 결과를 구분해서 읽는 것이 좋습니다.

이전 Sonnet 4.6 비교에서는 모든 평가 범주에서 개선됐다고 보고했습니다. 개선 폭은 여러 도구를 쓰는 과제에서 **+11.9%p**, 코드 분석에서 **+47.5%p**였고, 작업당 입력 토큰은 **47.8K에서 26.5K로 약 45% 감소**했습니다. 이 결과는 위의 GPT-5.5 Chat·Opus 4.8 표와 별도 비교입니다.

모델 이름은 논문에 사용된 표기를 그대로 유지했습니다. 연구 당시 두 harness에서 사용할 수 있었기 때문에 비교 대상으로 선정된 것이며, 논문은 이후 Microsoft Copilot harness가 reasoning 모델, Standard harness가 chat 모델에 초점을 맞췄다고 설명합니다. 이를 현재 모든 환경의 모델 선택 목록으로 해석해서는 안 됩니다.

### 호출은 늘었는데 효율 지표가 좋아진 이유

루프가 같은 문맥에 새 관찰을 덧붙이면, 이전에 처리한 긴 접두 문맥을 다시 사용할 수 있습니다. 반면 Standard harness는 의도 파악·계획·입력 확인마다 서로 다른 프롬프트를 구성하므로 호출 사이에 재사용할 접두 부분이 적습니다.

논문은 이를 비교하기 위해 다음 지표를 사용합니다.

```text
캐시 정규화 입력 토큰
= 캐시되지 않은 입력 토큰 + 정규화 계수 × 캐시 읽기 토큰
```

**15~21% 감소를 고객 청구액이나 Copilot Credits의 동일 비율 절감으로 읽으면 안 됩니다.** 논문은 이 수치가 제공자와 무관한 효율 비교이며, 가격·비용·마진을 산출할 수 있는 자료가 아니라고 명시합니다.

또한 **호출당 지연 감소는 전체 작업 시간이 10~36% 단축됐다는 뜻이 아닙니다.** 호출 횟수 자체가 늘어나므로 전체 시간은 반복 횟수와 도구 실행 시간 등에 달려 있습니다. 빠른 단답과 긴 업무의 완료를 같은 기준으로 비교하지 않는 것이 핵심입니다.

## 도구가 실패했을 때: 계속 실행과 실제 복구는 다르다

운영 텔레메트리에서는 실패한 도구 호출 뒤 추가 호출이 있었는지, 그리고 실패했던 동일 도구가 같은 작업·대화 안에서 나중에 성공했는지를 조사했습니다.

| 채널 | Copilot harness: 실패 뒤 도구 호출 계속 | Copilot harness: 동일 도구 나중에 성공 | Standard: 도구 호출 계속 | Standard: 동일 도구 나중에 성공 |
|---|---|---|---|---|
| Autonomous | 91% | 45% | 0.2% | 0.1% |
| M365 Copilot | 84% | 39% | 7% | 5% |

따라서 **84~91%는 실패 복구 성공률이 아니라, 실패 뒤에도 작업을 이어간 비율**입니다. 동일 도구의 후속 성공 비율은 39~45%이며, 다른 도구로 목표를 달성한 경우까지 이 숫자에 포함된다고 볼 수는 없습니다. 이 지표들은 관찰된 실행 행동이지 전체 업무 완료율도 아닙니다.

논문은 도구를 열 번 호출하고 각 호출이 5% 확률로 실패하는 예를 듭니다. 독립적인 실패를 가정하면 적어도 한 번 실패할 확률은 약 40%입니다. 복잡한 업무에서 “각 도구가 대체로 잘 동작한다”만으로 충분하지 않고, 실패 이후의 행동 설계가 필요하다는 설명입니다.

운영에서 Microsoft Copilot harness는 턴의 절반 이상에서 내부 CLI 도구를 사용했고, Standard harness의 별도 활성화 기능인 code interpreter는 1% 미만의 턴에서 사용됐다고 보고합니다. 도구 호출 수의 90·99백분위도 두 채널에서 2~4배 높았습니다. 다만 메이커가 원래 더 길고 데이터가 많은 업무에 Copilot harness를 선택하는 효과가 있으므로, 운영 사용량 차이를 그대로 인과적 성능 향상으로 해석해서는 안 됩니다.

## Excel 커넥터 사례: 무작정 재시도보다, 실패할 호출을 줄이기

논문은 **Excel Online (Business)** 커넥터를 개선한 과정을 소개합니다. 핵심은 모델이 매개변수나 통합 문서 구조를 추측하지 않고 먼저 확인하도록 돕는 것입니다.

1. **2026년 7월 2일**, 드라이브·폴더·통합 문서의 테이블·열 구조 등 필요한 정보를 조회하는 읽기 전용 보조 도구를 harness 내부 구현에 추가했습니다.
2. 운영 실패 데이터를 동작별로 분석해, 테이블이 없는 통합 문서에 `GetTables`를 호출하는 등 성공할 수 없는 요청을 찾았습니다.
3. **7월 28일**, 텔레메트리에 기반해 구현을 조정했습니다. 구조를 먼저 확인하고 가능한 동작만 호출하도록 개선한 사례입니다.

모든 Excel Online 동작의 **성공 호출 수 ÷ 전체 호출 수**로 측정한 성공률은 **85.6%에서 96.3%로 상승**했습니다. 메이커가 에이전트 설정을 바꿀 필요는 없었다고 논문은 설명합니다. 관측 그래프의 기간은 2026년 6월 13일부터 8월 10일까지이며, 개선된 수준이 해당 관측 기간 끝까지 유지됐다고 보고합니다.

원래 94% 이상 성공하던 고빈도 목록 조회 동작은 큰 변화가 없었고, 개선은 주로 테이블과 행을 읽고 쓰는 동작에 집중됐습니다. 남은 실패는 스크립트 실행과 테이블 생성에 집중됐다고 합니다. **96.3%를 모든 Excel 업무의 완료율이나 무오류 보장으로 확대하면 안 됩니다.**

이 사례는 재시도로 복구하는 능력과, 애초에 불가능한 요청을 줄이는 도구 품질 개선이 서로 보완적이라는 점을 보여 줍니다.

## 경쟁 비교 수치는 어떻게 읽어야 할까

논문은 **복잡한 업무 프로세스 자동화 테스트 케이스 20개**로 구성된 평가에서 Microsoft Copilot harness의 완료율이 **65%**, 이름을 밝히지 않은 주요 경쟁 플랫폼은 **36%**였다고 보고합니다.

두 시스템의 최종 결과를 같은 성공 기준으로 판정했다고 설명하지만, 이는 **특정 시점의 단일 평가 묶음**입니다. 논문도 순위가 아니라 스냅샷이라고 명시합니다. 경쟁사 이름을 추정하거나 모든 업무에서 29%p 우위라고 일반화할 근거는 없습니다.

실행 날짜·횟수·모델 버전·설정은 결과와 함께 기록돼 요청 시 재현과 입증이 가능하다고 서술돼 있으나, 공개 본문에는 그 상세 값이 모두 제시되지는 않습니다. 구매나 플랫폼 선정의 최종 근거로 삼으려면 자사 데이터와 업무 조건으로 평가해야 합니다.

## 국내 조직이 적용할 때의 체크포인트

다음은 논문의 결과를 바탕으로 정리한 **도입·평가 권고**입니다. 원문에 제시된 필수 설정 절차나 새로운 제품 기능 목록은 아닙니다.

### 먼저 업무 유형을 구분하기

짧은 질의응답, 입력 확인, 빠른 응답이 중요한 대화형 업무는 Standard harness가 가진 장점과 맞습니다. 반면 대량 데이터, 여러 시스템 대조, 코드 검증, 문서·스프레드시트 산출물, 사람이 상시 대기하지 않는 업무는 Microsoft Copilot harness를 검토할 이유가 있습니다.

논문이 예로 든 한 달치 청구서 검토, 두 시스템의 기록 대조, 폴더의 문서를 이용한 보고서 작성부터 작은 평가 과제를 만드는 방법이 좋습니다. 단순 채팅 데모만으로 긴 업무의 적합성을 판단하지 않는 것이 중요합니다.

### 평가의 전제조건과 성공 기준 준비하기

실제 테넌트에서 사용할 수 있는 harness·모델·기능과 연결 도구를 먼저 확인하고, 허용된 데이터와 테스트 계정을 준비합니다. 원문에는 모든 고객에게 적용되는 GA 일정, 지역별 제공 범위, 라이선스 조건, 활성화 클릭 경로가 나오지 않습니다. 이 글만 보고 바로 사용할 수 있다고 가정하지 않아야 합니다.

평가에서는 단순히 응답이 생성됐는지가 아니라 **행 누락, 중복, 합계 불일치, 근거 없는 설명, 산출물 형식**까지 성공 기준에 넣는 것이 좋습니다. 두 방식을 비교한다면 가능한 한 같은 모델·데이터·도구·성공 기준을 유지하고, 모델이 바뀌면 다시 확인합니다.

### 자율 실행의 경계와 종료 조건 정하기

메이커 지침에는 업무 절차와 함께 **허용한 작업, 승인이 필요한 작업, 실패 시 보고 조건, 실행 예산**을 명시하는 것이 좋습니다. 특히 쓰기 동작을 다시 시도할 때 중복 등록·중복 전송이 생기지 않는지 확인해야 합니다.

도구 실패 뒤 계속 호출하는 비율만 높이는 대신, 실제 업무 완료율·동일 도구 복구율·부작용·전체 시간도 함께 봐야 합니다. 권한 오류처럼 재시도로 해결되지 않는 문제를 명확히 보고하는 것 역시 업무 품질입니다.

### Excel과 대량 데이터의 구조를 사전 확인하기

Excel 업무에서는 통합 문서에 실제 테이블이 정의돼 있는지, 필요한 열과 식별자가 있는지 확인하는 과제를 넣을 수 있습니다. 대량 데이터를 파일로 처리하더라도 읽기·쓰기 권한과 세션 종료 후 보존 조건은 별도 점검합니다.

“캐시 덕분에 효율이 좋아졌다”는 연구 결과와 실제 조직의 라이선스·용량·과금은 구분해 검토해야 합니다. 특히 호출당 지연뿐 아니라 사용자가 결과를 받기까지 걸린 전체 시간을 측정하는 것이 좋습니다.

## 마무리: 모델 선택만큼 중요한 실행 구조

이 논문의 메시지는 “더 많은 호출이 항상 더 좋다”가 아닙니다. **문맥을 유지하는 루프, 코드와 파일을 활용하는 환경, 런타임의 거버넌스, 실패를 줄이는 도구 개선**을 결합하면 복잡한 업무에 맞는 실행 구조를 만들 수 있다는 것입니다.

국내 Copilot·에이전트 담당자에게는 짧은 답변의 품질과 긴 업무의 완료율을 분리해서 평가하는 출발점이 됩니다. 공개 수치는 Microsoft의 특정 평가·관측 조건에서 나온 결과이며, 실제 도입에서는 자사 업무의 완료 기준과 권한·예산 경계를 함께 검증해야 합니다.
