# 모델보다 업무 지침이 중요할 때: SPFx Dev Skills 105회 평가가 보여준 것

코딩 에이전트가 프로젝트를 빌드 가능한 상태로 만들었다고 업그레이드를 완전히 끝낸 것은 아닙니다. 의존성, 설정, 도구 체인, React API까지 목표 버전에 맞게 변경했는지 확인해야 합니다.

Microsoft 365 Developer Blog는 **SPFx Dev Skills v1.1.2**와 함께 105회 평가 결과를 공개했습니다. 이번 결과는 “가장 큰 모델을 고르면 된다”보다 **해당 작업에 맞는 지침과 평가 기준을 제공하는가**가 중요할 수 있음을 보여줍니다.

---

## v1.1.2에서 달라진 내용

업데이트는 **SharePoint Framework 1.24.1** 프로젝트 생성·업그레이드와 기존 React 코드의 **React 18 API 전환**을 다룹니다. Heft, 의존성 버전, 대상 SPFx 릴리스가 지원하는 Node.js 버전 등 도구 요구사항도 포함합니다.

또한 CLI for Microsoft 365의 업그레이드 보고서를 끝까지 읽고 적용하도록 안내하고, Fluent UI v9와 PnPjs 권고를 갱신했습니다. 설치·업데이트 방법은 [SPFx Dev Skills 저장소](https://github.com/SharePoint/spfx-dev-skills)에서 확인할 수 있습니다.

## 105회 평가는 어떻게 구성됐나요?

평가 대상은 기존 프로젝트를 SPFx 1.24.1로 올리는 **한 가지 시나리오**입니다. 새로 스캐폴딩한 1.24.1 프로젝트의 의존성·설정과 React 18 API 변경을 기준으로 채점했습니다. 100%는 이 루브릭의 모든 검사를 만족했다는 의미입니다.

7개 에이전트·모델 조합에 대해 스킬 없음, v1.0, v1.1.2의 세 조건을 각각 5회 실행했습니다. 즉 **7 × 3 × 5 = 105회**이며, 모두 Windows에서 수행했습니다. 표의 점수와 비용은 구성별 5회 평균입니다.

## 품질과 비용을 함께 보기

아래는 원문의 세 조건 중 스킬 미사용과 최신 버전을 비교한 요약입니다. 비용은 실행당 **추정 추론 비용(미화)**으로, 제품 구독료나 실제 고객 청구액과 동일한 지표가 아닙니다.

| 에이전트·모델 | 스킬 없음 점수 | v1.1.2 점수 | 스킬 없음 비용 | v1.1.2 비용 |
|---|---:|---:|---:|---:|
| Copilot Chat · Sonnet 5.5 | 47% | 100% | $0.49 | $0.40 |
| Copilot Chat · Opus 5.5 | 94% | 100% | $1.24 | $0.82 |
| Copilot Chat · GPT-6 Luna | 27% | 100% | $0.03 | $0.03 |
| Copilot Chat · GPT-6.1 Terra | 59% | 98% | $0.33 | $0.23 |
| Copilot Chat · Copilot Fusion | 32% | 100% | $0.01 | $0.02 |
| Claude Code · Sonnet 5.5 | 41% | 100% | $0.07 | $0.16 |
| Claude Code · Opus 5.5 | 94% | 100% | $0.25 | $0.32 |

이전 v1.0은 모든 조합을 93~94%로 끌어올렸고, v1.1.2에서는 7개 중 6개가 100%, 나머지 하나가 98%에 도달했습니다.

동일한 최신 스킬을 사용한 Copilot Chat 안에서 GPT-6 Luna의 평균 비용은 $0.03, Opus 5.5는 $0.82로 약 **27배** 차이였습니다. Fusion은 $0.02로 약 **41배** 낮았습니다. 다만 Fusion은 요청마다 모델을 선택하는 라우터이므로 결과를 특정 단일 모델의 성능으로 해석해서는 안 됩니다.

## 좋은 지침도 비용을 늘릴 수 있습니다

품질 향상이 항상 비용 절감을 의미하지는 않습니다. 예를 들어 Claude Code의 Opus 5.5는 94%에서 100%로 개선됐지만 비용은 $0.25에서 $0.32로 늘었습니다. v1.0과 비교하면 최신 스킬의 추정 비용은 7개 중 6개 조합에서 더 높았습니다.

원문은 전체 업그레이드 보고서를 읽고 적용하는 과정이 추가 토큰 사용에 영향을 줄 수 있다고 설명합니다. 따라서 조직에서 스킬을 평가할 때는 정확도만이 아니라 비용과 작업 완결성도 함께 비교하는 것이 좋습니다.

## 실제 수정으로 이어진 실패 분석

평가 중 일부 에이전트는 CLI로 업그레이드 보고서를 만들었지만 일부만 읽었습니다. 보고서 뒤쪽의 작업을 놓쳐 프로젝트가 부분적으로만 업그레이드되는 문제가 생겼습니다.

이를 해결하기 위해 스킬은 **여러 번 나눠 읽더라도 마지막 `## Summary`까지 전체 보고서를 확인**하도록 명시했습니다. 점수는 결과를 알려주고, 에이전트의 행동 기록은 왜 실패했는지를 보여준다는 점이 중요합니다.

## 도입할 때의 한계와 시작 방법

이번 결과는 하나의 SPFx 업그레이드 과제에 대한 평가입니다. 모든 개발 업무에서 작은 모델이 같은 품질을 낸다거나, 100% 점수가 운영 무결함을 보장한다는 뜻은 아닙니다. 커뮤니티가 평가를 직접 실행할 수 있도록 공개하는 작업과 평가 시나리오 확대도 향후 계획으로 소개됐습니다.

SharePoint 개발팀은 최신 스킬을 적용하고 실제 프로젝트의 업그레이드 결과를 검토해 보시기 바랍니다. 모델 선택을 먼저 고정하기보다 대표 과제, 명확한 체크리스트, 실패 행동 기록을 묶어 비교하는 방식이 이번 발표에서 얻을 수 있는 실용적인 교훈입니다.
