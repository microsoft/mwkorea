# 몇 시간씩 일하는 AI 에이전트는 어떻게 학습할까? Microsoft AI의 Rocket 강화학습 인프라

메일 한 통을 요약하는 AI와 코드를 수정하고 도구를 호출하며 몇 시간 동안 문제를 해결하는 AI는 학습 과정에서도 다른 부담을 만납니다. 모델이 작업을 수행하는 동안 학습은 계속 진행되고, 오래 걸린 작업의 결과는 이미 이전 모델 버전의 경험이 될 수 있습니다.

Microsoft AI는 미국 현지 2026년 11월 23일 공개한 **RL infrastructure at Microsoft AI**에서 자체 강화학습 프레임워크 **Rocket**의 설계를 설명했습니다. 원문에 명시된 발행 시각은 한국 시간으로 **11월 24일 02:24:32**입니다. 이 글의 날짜는 그 KST 날짜를 사용합니다.

한국의 Copilot·에이전트 독자에게는 새로운 버튼이나 라이선스보다 **장시간 작업을 수행하는 모델의 품질과 안정성을 어떤 방식으로 개선하는가**에 관한 소식입니다. 원문은 MAI 내부 학습 시스템을 다루며, Rocket의 공개 서비스 제공이나 특정 Copilot 제품의 MAI Base 2 적용을 발표하지 않습니다.

## 출발점: 짧은 후처리가 아니라 긴 강화학습

Microsoft AI는 **3조 파라미터의 기반 모델 MAI Base 2**를 Rocket으로 후속 학습 중이라고 설명합니다. 이전에는 MAI Base 1을 추론 모델 MAI Thinking 1로 발전시키는 데 Rocket을 사용했고, 이번에는 더 큰 모델에 맞춰 확장했습니다. 원문은 이 작업이 **MAI Code 2 모델과 별개**라는 점도 명시합니다.

핵심 전제는 강한 외부 교사 모델의 결과를 증류해 출발하는 대신, 기반 모델에서 강화학습 자체를 통해 능력을 끌어올리는 것입니다. Microsoft AI는 이 학습 방식에서 **수천 대의 GPU로 수주~수개월 동안 수천 번의 학습 단계**를 이어갈 필요가 있다고 설명합니다. 이는 원문이 제시한 학습 규모와 설계 목표이지, 모든 개별 실행의 정확한 GPU 수나 완료 일정을 공개한 것은 아닙니다.

실행이 길어지면 작은 수치 오차와 비효율도 누적됩니다. 따라서 Rocket은 다음 세 문제를 중심으로 설계되었습니다.

| 문제 | 발생 이유 | 운영상 영향 |
|---|---|---|
| 정책 지연, staleness | 에이전트 작업이 끝나기 전에 학습 모델이 여러 차례 갱신됨 | 오래된 정책으로 생성된 데이터를 최신 정책 학습에 사용하게 됨 |
| 수치 일관성 | 추론과 학습의 정밀도·커널·병렬화 방식이 다름 | 같은 모델과 입력에서도 토큰 확률이 달라져 학습이 불안정해질 수 있음 |
| 장애 복구와 탄력성 | 장기간 GPU 장애가 발생하고 작업 구성·자원 수요가 변함 | 전체 재시작을 반복하면 시간과 GPU 사용량이 낭비됨 |

## Rocket은 무엇을 연결하는 시스템인가

Microsoft AI는 학습기와 학습 프레임워크, Rocket, 그리고 **자체 유지보수하는 SGLang 포크 기반 추론 엔진**을 함께 개발·운영합니다. 세 계층의 인터페이스를 함께 설계해 강화학습 루프 전체를 최적화한다는 설명입니다.

모든 기반 기술을 새로 만든 것은 아닙니다. 노드 할당에는 **Kubernetes 또는 Slurm**, 컴포넌트 실행에는 **Ray actor**를 사용합니다. 오픈소스 RL 프레임워크인 [verl](https://github.com/verl-project/verl)과 [slime](https://github.com/THUDM/slime)도 좋은 기반으로 언급하지만, Microsoft AI는 자사의 장기 학습과 모델 구조에 맞춘 통합 제어가 필요했다고 설명합니다. 자체 포크와 통합을 유지하는 비용도 인정합니다.

여기서 **rollout은 하나의 문제를 해결하려는 한 번의 시도**, policy는 토큰을 생성하는 현재 모델의 행동 정책, sampler는 그 정책으로 응답을 생성하는 추론 계층, learner는 경험 데이터를 받아 가중치를 갱신하는 학습 계층입니다.

### 한 번의 학습 루프

Rocket의 장기 학습은 **GRPO, Group Relative Policy Optimization**을 기반으로 합니다. 동일한 문제에 대한 여러 시도의 보상을 비교해 상대적인 학습 신호인 advantage를 계산합니다.

1. **Controller가 문제를 선택합니다.** 커리큘럼에서 작업을 골라 problem worker에 전달합니다.
2. **Problem worker가 여러 시도를 배정합니다.** Rollout worker 풀에서 동시 실행하며, 각 worker도 여러 요청을 처리합니다.
3. **에이전트가 추론과 도구 실행을 반복합니다.** Sampler에 모델 응답을 요청하고 tool dispatcher를 통해 작업 환경에 접근합니다. 샌드박스 실행 환경, 검색 서비스, MCP 서버의 도구 등이 원문에 예시로 등장합니다.
4. **평가기가 실행 경로를 채점합니다.** 필요하면 최종 환경 상태까지 평가합니다. Rollout worker는 경로 데이터를 저장하고 점수와 저장 위치 참조를 반환합니다.
5. **같은 문제의 시도를 묶어 비교합니다.** Problem worker가 그룹 평가를 수행하고 GRPO advantage를 계산합니다.
6. **Controller가 학습 배치를 구성합니다.** 하나 이상의 모델 턴을 포함한 training segment를 묶어 전달하고, learner는 저장된 토큰 ID와 샘플링 로그 확률을 읽어 정책을 갱신합니다.
7. **새 가중치와 복구 상태를 반영합니다.** Controller가 주기적으로 sampler를 갱신하며, 체크포인트에는 learner와 controller 상태를 보존합니다.

복잡한 에이전트 학습은 최종 답만 채점하는 문제가 아니라, **도구 실행을 포함한 전체 경로를 수집·평가하고 이를 최신 학습 상태에 연결하는 문제**라는 점을 보여줍니다.

## 오래된 경험을 학습하는 문제: staleness 관리

원문은 간단한 지시 이행 작업이 몇 분에 끝나는 반면, 소프트웨어 엔지니어링 같은 장기 에이전트 작업은 몇 시간이 걸릴 수 있다고 설명합니다. Rocket은 비동기 시스템이므로 작업이 진행되는 동안에도 learner는 갱신됩니다.

정책 지연은 **토큰 생성에 사용한 정책 버전과, 그 토큰을 학습하는 시점의 learner 버전 사이의 차이**로 측정합니다. 단계 사이 시간이 대략 일정하면 다음처럼 생각할 수 있습니다.

```text
정책 지연 ≈ 생성 시점의 sampler 버전 지연
          + (토큰 학습 시각 − 토큰 생성 시각) / 학습 단계 간 시간
```

뒤의 항에는 작업 완료까지의 시간, 같은 GRPO 그룹의 다른 작업을 기다리는 시간, learner 투입 대기 시간이 모두 포함됩니다. 버전 차이가 커지면 sampler와 learner의 로그 확률 차이도 커질 수 있어 학습 안정성에 영향을 줍니다.

### 네 가지 제어와 그 대가

| 제어 | 원문의 구현·관찰 | 함께 고려할 비용 |
|---|---|---|
| Sampler를 자주 갱신 | 예시에서는 4개 학습 단계마다 갱신하므로 생성 시점 버전 지연은 0~3단계 | 거대한 가중치를 많은 추론 복제본에 전송해야 함 |
| 기존 rollout을 먼저 완료 | 시작 시각이 이른 rollout의 추론 요청을 우선 처리하고, 진행 중 작업 수를 추론 용량에 맞춰 자동 조절 | 새 작업이 첫 응답을 오래 기다릴 수 있음 |
| 실패한 rollout을 제외 | 실패 작업의 재시도로 정상 완료 작업까지 장기간 기다리지 않게 함 | 실패 사례가 빠져 GRPO 기준값에 잡음·편향이 생길 수 있음 |
| 추론을 병목으로 유지 | Learner에 GPU를 여유 있게 할당해 완료 데이터의 학습 대기를 줄임 | Learner GPU가 부분적으로 유휴 상태가 됨 |

가중치 전송은 두 단계입니다. 먼저 선택된 sampler 엔진이 learner에서 묶인 파라미터 청크를 가져오고, 이어 추론 복제본들의 대응 rank에 분배합니다. 복제본마다 learner가 직접 전송하는 부담을 줄이는 방식이며, **원문의 현재 구성과 실행에서는 약 15초**가 걸렸습니다. 모든 환경에서 보장되는 수치는 아닙니다.

대기 시간의 구체적인 예도 중요합니다. 원문의 도식에서 각 rollout은 첫 추론 요청까지 **24분**을 기다리고, 가장 빠른 rollout은 같은 그룹의 가장 느린 시도가 끝날 때까지 **7.6시간**을 기다립니다. 반면 완료된 그룹의 controller 대기는 **12초**입니다. 첫 토큰 생성 전 대기는 정책 지연을 직접 늘리지는 않지만, 이미 확보한 VM 등 자원을 점유할 수 있으므로 타임아웃 설계에 포함해야 합니다.

또 하나의 역설은 **추론 서버를 늘리는 것만으로 정책 지연이 줄지는 않는다**는 점입니다. 배치 크기를 그대로 두면 학습 배치를 더 빨리 모으고 학습 단계 간 시간이 짧아집니다. 동일한 길이의 rollout이 진행되는 동안 더 많은 모델 갱신이 일어나므로, 시간은 같아도 버전 기준 지연은 오히려 커질 수 있습니다.

## 메모리는 줄이되 계산은 맞추기: MXFP8과 BF16

MAI Thinking 1에서는 sampler 가중치와 KV 캐시를 BF16으로 유지했습니다. 더 큰 MAI Base 2에서는 일부 저장에 **MXFP8**을 사용하되 계산 시에는 BF16으로 되돌리는 전략을 사용합니다.

### MoE 가중치

MoE expert 가중치는 모델 파라미터의 **95% 이상**을 차지합니다. 이를 BF16 대신 MXFP8으로 저장하면 sampler의 가중치 메모리 사용량이 거의 절반으로 줄어, expert parallelism의 분할 규모와 추론 복제본당 GPU 수를 낮출 수 있습니다.

하지만 MXFP8로 행렬 곱까지 수행하면 sampler와 learner의 로그 확률 차이가 더 커졌습니다. Microsoft AI는 **저장은 MXFP8, 역양자화 후 계산은 BF16**으로 분리했습니다. Learner에서도 MoE 가중치를 MXFP8로 양자화했다가 즉시 BF16으로 복원해 계산하여 sampler의 양자화 효과를 재현합니다.

### KV 캐시

Global attention의 KV 캐시도 MXFP8로 저장하고 attention 커널 안에서 BF16으로 복원해 계산합니다. Learner에는 대응하는 fake quantization을 적용합니다. 캐시가 작아지면 긴 시퀀스와 더 많은 동시 rollout을 지원하고, 메모리 압박으로 KV 데이터를 외부로 옮기거나 요청을 중단·재처리하는 부담을 줄일 수 있습니다.

모든 attention 계층을 양자화하지는 않습니다.

- MAI Base 2의 local attention과 global attention 비율은 **5:1**입니다.
- Local attention KV 캐시는 **BF16을 유지**합니다.
- 수치 안정성을 위해 **마지막 3개의 global attention 계층도 BF16**을 유지합니다.
- 나머지 global attention 계층의 KV 캐시는 MXFP8 저장을 사용합니다.

이 구성은 BF16 KV 캐시 구성과 비교해 **global-context 토큰을 약 67% 더 수용**하면서 local attention 캐시 용량은 대략 동일하게 유지했다고 설명합니다. 이는 해당 캐시 구성의 수용량 비교로, 모델의 전체 컨텍스트 한도가 일괄 67% 늘었다는 뜻은 아닙니다.

## 같은 체크포인트라도 계산이 다르면 학습은 달라집니다

저장·계산 정밀도를 맞추는 것만으로 충분하지 않습니다. GPU 간 합산 순서, 병렬화, 커널의 타일 구성과 중간 반올림이 달라도 토큰 확률에 차이가 생길 수 있습니다.

Microsoft AI는 동일한 체크포인트와 입력에서 **sampler와 learner의 계산을 비트 단위로 일치**시켰으며, 눈에 띄는 성능 저하는 없었다고 보고합니다. 이를 구현하기 위한 핵심 변경은 다음과 같습니다.

| 영역 | 일치시키기 위한 설계 |
|---|---|
| Attention 출력 projection | Sampler의 attention에는 TP를 유지하되 출력 projection 가중치를 복제합니다. Head 출력을 all-gather한 뒤 토큰의 전체 projection을 한 GPU에서 계산해 projection 뒤의 GPU 간 reduction을 없앱니다. Learner는 TP 없이 대응하는 합산 순서를 사용합니다. |
| MoE expert 출력 결합 | Expert는 EP로 분산하고 개별 expert 내부에는 TP를 쓰지 않습니다. All-to-all로 expert별 출력을 토큰의 원래 장치로 돌려보낸 뒤, 정규화된 routing 가중치로 **FP32 로컬 가중 합산**을 수행해 누적 정밀도와 합산 순서를 맞춥니다. |
| Attention 커널 | 공통 **FA4 구현**을 learner forward, sampler prefill, sampler decode에 사용합니다. Sliding-window attention의 K-block 경계와 타일을 정렬하고 유효 창 밖을 마스킹합니다. Split당 KV 토큰 수와 split 경계도 일치시킵니다. |

비교 실험은 **활성 파라미터 7B, 전체 파라미터 180B**인 더 작은 모델 L42에서 수행되었습니다. 같은 체크포인트로 시작해 약 한 달 간격으로 실행한 두 학습을 비교했으며, 수치 일관성을 개선한 실행이 비슷한 학습 단계에서 더 높은 평가 점수를 보였다는 설명입니다.

이 결과를 3조 파라미터 MAI Base 2의 동일한 통제 실험으로 바꿔 읽거나, 모든 모델에서 같은 개선 폭이 보장된다고 해석하면 안 됩니다. 원문이 공개한 것은 특정 비교 실험과 Microsoft AI의 관찰입니다.

## 장애가 나도 전체 학습을 멈추지 않기

수주 이상 실행하면 장애는 예외적인 사건이 아니라 운영 조건입니다. Rocket은 학습 루프와 감독 계층을 분리하고, **진행을 복구하는 데 필요한 최소 범위**부터 수리합니다. 생존 여부뿐 아니라 학습 진행도도 검사해 멈춘 프로세스를 비정상으로 봅니다.

### Learner만 복구

Learner가 실패하면 새 문제의 접수를 잠시 중단하고 learner rank를 종료합니다. 각 rank의 NCCL 타임아웃을 끝까지 기다리지 않고 learner를 다시 구성해 최신 체크포인트를 복원한 뒤 기존 controller에 연결합니다.

이때 controller, rollout worker, 추론 서비스는 계속 살아 있으며 커리큘럼 상태와 유효한 대기 작업을 보존합니다. 원문의 실행에서는 learner만 복구하는 데 **약 5분**이 걸렸고, 최근 실행에서 이 방식이 GPU 시간의 **7% 이상을 절감**했다고 보고합니다. 복구 중 추론을 유지하는 선택은 GPU 유휴 시간을 줄이는 대신 추가 정책 지연을 받아들이는 절충입니다.

### 추론 복제본과 작업 내부 복구

실패한 추론 복제본은 정상 복제본이나 learner를 재시작하지 않고 교체합니다. 반복 장애로 살아 있는 추론 worker의 비율이 설정 임계값 아래로 내려가면 클러스터 스케줄러 수준에서 작업을 다시 시작해 용량을 복원합니다.

국소 복구로 충분하지 않으면 기존 Ray 작업 안에서 재구성하는 **In-Job Recovery**를 시도하고, 그것으로도 진행이나 건강한 용량을 복구할 수 없으면 클러스터 수준으로 재큐잉합니다. 원문은 작업 내부 복구가 클러스터 스케줄링·컨테이너 시작 비용을 줄여 **학습 연산의 0.42%를 절감**했다고 설명합니다.

Ray head와 Rocket CPU actor는 **CPU 전용 노드**에서 실행합니다. Microsoft AI의 배포에서는 이 노드가 GPU 노드보다 안정적이었으며, GPU 측 장애가 감독·제어 서비스까지 중단시키는 위험을 줄이기 위한 선택입니다.

## 자원과 학습 설정을 실행 중에 조절하기

학습이 진행되면 rollout 길이, 모델 능력, 문제의 조합이 달라져 learner와 추론의 균형도 변합니다. Rocket은 자원 크기를 조절하는 탄력성과 실행 설정을 조절하는 탄력성을 구분합니다.

### 자원 탄력성

Learner, 추론 worker, controller 서비스를 각각 확장·축소합니다. 추론 worker는 새로운 구성이 들어오면 바로 조절할 수 있지만, learner는 버리는 연산을 줄이기 위해 **다음 체크포인트 저장 뒤** 크기를 조절합니다.

Rack-scale Blackwell 클러스터에서는 GPU 개수만 충분하다고 필요한 worker 그룹을 만들 수 있는 것은 아닙니다. 연결 토폴로지 제약이 있기 때문입니다. 클러스터 스케줄러가 작업에 노드를 할당하고, Rocket이 그 안에서 연결 조건을 만족하는 그룹을 컴포넌트에 배치하며 반환된 노드를 재사용합니다.

또한 learner slice 하나를 교체할 수 있는 크기의 예비 노드 그룹을 유지합니다. Slice가 실패하면 예비 그룹으로 교체하고 autoscaling으로 예비 용량을 보충합니다. 이는 **예약 자원 비용과 빠른 복구 사이의 절충**이며, 적합한 클러스터 용량이 남아 있어야 반복 교체가 가능합니다.

### 실행 설정 탄력성

Rocket은 타입과 유효성을 검증한 런타임 설정으로 다음을 조절합니다.

- 추론 용량과 동시 실행 수.
- 새 작업 접수와 정책 지연 한도.
- 배치 구성 방식.
- 문제 유형별 혼합 가중치.

컴포넌트는 학습 단계 완료 후나 샘플링 직전처럼 정해진 경계에서 변경을 적용합니다. 원문은 분석한 학습 구간에서 런타임 탄력성이 **학습 연산 효율을 9.88% 개선**했다고 보고합니다. 이 수치와 복구 관련 수치는 동일한 일반 보장이나 단순 합산 가능한 전체 절감률로 제시된 것이 아닙니다.

## 성능 전망은 어떻게 읽어야 할까요

Microsoft AI는 다수의 공개·비공개 평가를 합친 자체 **aggregate reasoning benchmark**에서 모델이 Claude Opus 4.8의 성능을 넘었으며, 몇 주 안에 GPT-5.6 Sol을 넘어설 것으로 예상한다고 원문에서 밝혔습니다.

여기서 현재 성과와 미래 전망을 분리해야 합니다. 이는 **Microsoft AI가 원문 시점에 보고한 자체 종합 평가와 전망**이며, 독립 기관이 모든 업무에서의 우위를 검증했다는 뜻은 아닙니다. “몇 주 안”이라는 표현도 완료된 사실이나 제품 출시 일정이 아닙니다. 한국어 업무, 실제 사내 데이터, 특정 에이전트의 성능은 별도의 평가가 필요합니다.

원문은 지속적인 학습 과정에서 성능이 정체하거나 불안정해지지 않고 상승했다고 설명합니다. 하지만 공개 자료만으로 특정 조직의 Copilot 품질 개선 시점이나 모델 접근 권한을 예측할 수는 없습니다.

## Copilot·에이전트 도입 담당자가 가져갈 세 가지 관점

대부분의 조직이 Rocket 같은 기반 모델 학습 시스템을 직접 운영할 필요는 없습니다. 다만 이 연구를 통해 실제 에이전트 설계에도 적용할 질문을 얻을 수 있습니다. 다음은 **원문의 인프라 설계에서 도출한 실무적 시사점**입니다.

**첫째, 장시간 작업의 품질은 최종 답만으로 평가하지 않습니다.** 도구 호출 경로, 대기 시간, 재시도, 실패 유형과 사람의 검토를 함께 관찰해야 합니다. 오래 걸린 작업과 실패한 작업을 숨기면 품질 평가가 편향될 수 있습니다.

**둘째, 효율 개선은 정확성 검증과 함께 진행합니다.** 양자화나 실행 방식 변경이 메모리를 줄여도 결과 품질을 유지하는지는 따로 검증해야 합니다. 원문의 MXFP8 저장과 BF16 계산 분리는 최적화가 단일 정밀도 선택으로 끝나지 않는다는 사례입니다.

**셋째, 복구 범위와 비용을 처음부터 설계합니다.** 전체 워크플로를 재실행하기 전에 정상 작업을 보존할 수 있는지, 특정 도구나 실행 단위만 복구할 수 있는지 검토할 수 있습니다. 더 빠른 복구를 위한 예비 용량에는 비용이 있고, 처리량을 늘리는 결정도 지연·품질과 함께 평가해야 합니다.

이러한 관점은 개별 Copilot 제품 설정을 그대로 설명하는 것이 아닙니다. 조직이 도입하는 에이전트의 운영 기준을 세울 때 참고할 수 있는 시스템 설계 원칙입니다.

## 시작하기와 마무리

기술 내용을 더 깊게 읽으려면 원문에 연결된 [Rocket 기술 PDF](https://microsoft.ai/pdf/RL-Infrastructure-at-Microsoft-AI.pdf), [MAI Thinking 1 기술 보고서](https://microsoft.ai/pdf/mai-thinking-1.pdf), [MAI Base 2 사전 학습 소개](https://microsoft.ai/news/frontier-pre-training-at-microsoft-ai/)를 함께 참고할 수 있습니다. 도식과 비교 그래프는 원문·PDF에서 확인할 수 있으며, 이 글의 소개 이미지는 학습 성능 그래프가 아닙니다.

Rocket의 메시지는 **더 많은 GPU만으로 장기 에이전트 학습이 해결되지는 않는다**는 것입니다. 정책 버전의 시간차, 추론·학습 계산의 일치, 국소 장애 복구와 자원 재배치가 함께 맞아야 오랜 학습을 지속할 수 있습니다.

Copilot과 에이전트의 다음 발전을 이해할 때도 기능 발표뿐 아니라 그 뒤의 평가와 운영 설계를 함께 보는 것이 중요합니다. 이번 글은 그 기반을 보여주는 연구 소개이며, MAI Base 2나 Rocket의 GA·가격·Copilot 배포 일정을 발표한 소식은 아닙니다.
